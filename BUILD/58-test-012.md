## 2 — Is it checkable? **Yes, and it is checked now.**

`MAIN_WORK/scripts/check_player_strings.py`. It reads **Dart string literals**
in the play client, and three choices make it work rather than drown:

- **Comments are stripped.** This project's comments cite constantly and
  should; `///`, `//` and `/* */` go before anything is matched.
- **Prose only.** A literal counts as player-facing when it contains a space
  and a lower-case word. A key or a path — `weapon_r_1`,
  `items/weapons/blaster-rifle` — has no room to hide a citation. ⚠ That is a
  heuristic and it is stated, not hidden.
- **The play client only.** `Loom`'s user is an **author** and is owed the
  citation: its New Item dialog cites `PACKAGE-NAMING-01` on purpose and its
  writers emit a file header, not a screen. `--all` shows those eight.

⚠ **It found nine, not one.** The `— PT-559:` I typed was the newest; the
others had been on screen for slices — `STARTING-EQUIPMENT-01 §3` in the class
bar, `PT-701, PT-703` on the Equipment screen, `PT-92` on the Force bar, two
`[entry]`s and a `[requires]`.

⚠⚠ **And three TESTS asserted the citations were on screen**, so the suite
encoded the defect. They now assert the fact reaches the player and the
reference does not.

**Its limit, stated:** it cannot see a citation assembled at runtime from
pieces, or one that arrives from data. The data half is `check_annotations`;
between them the two halves are covered, and a string built by concatenation at
call time is not.
