# STUDY 01 — CONTAINER LAYER — RECORDS

Six records, one per archive type. Template per `STUDY/README.md`, unmodified.

Everything below was read from the shipped files of both games with parsers
written for this pass. Where something is **inferred** rather than read, the
record says so on the line.

Installs read:
`/mnt/ga/SteamLibrary/steamapps/common/swkotor` (K1, Windows build) and
`/mnt/ga/SteamLibrary/steamapps/common/Knights of the Old Republic II/steamassets`
(K2, Aspyr build with a native Linux `KOTOR2` binary).

## KEY — the master index of the read-only archives

**WHAT IT IS**
A single lookup table saying which big archive file every stock game resource
lives in, and where inside it.

**CONTAINER**
Not contained — it is a loose file at the install root, `chitin.key`. The engine
addresses it as `HD0:chitin` / `HD0:CHITIN` (both literals present in both
binaries).

**STRUCTURE**
Binary. Signature `KEY `, version `V1  `. Header carries BIF count, resource
count, and offsets to two tables.

- BIF table entry, 12 bytes: file size u32, filename offset u32, filename
  length u16, **drives bitmask u16**.
- Resource table entry, 22 bytes: ResRef[16], ResType u16, ResID u32.
- `ResID = (bifIndex << 20) | indexWithinBif`. Verified: the high bits span
  exactly `0..bifCount-1` in both games.

Filenames are stored with Windows separators (`data\2da.bif`) in both games,
including K2's Linux build.

**REFERENCES OUT**
To BIF files **by filename string**, and to a resource **by packed integer
index**, not by name. The name→location direction is the whole point of the
file; the reverse direction is a positional integer.

**REFERENCED BY**
The engine's resource manager at startup. No game data file references the KEY;
searched every 2DA in both games and both binaries — the only references are the
two `HD0:chitin` literals.

**SCOPE**
Game-global. One per installation.

**AUTHORED BY**
Generated by the build. Not hand-editable in any practical sense — every ResID
encodes a BIF index, so inserting a resource renumbers nothing but requires the
matching BIF to be rebuilt in step.

**READ WHEN**
Game start, once. Inferred from it being the only index for the BIF layer;
not confirmed against a running process.

**K1 vs K2**
- K1: 569,239 bytes, **26 BIFs**, **25,836 resources**. Drives mask `0x0001`.
- K2: 406,035 bytes, **11 BIFs**, **18,439 resources**. Drives mask `0x0000`.
- K1's non-zero drives mask is consistent with the CD-era multi-volume scheme;
  K2 zeroes it. That the field *means* CD volumes is inferred from the name and
  from the `HD0:` namespace, not read from behaviour.
- K2 consolidated: K1 spreads lightmaps across 13 separate BIFs
  (`lightmaps.bif`, `lightmaps2.bif` … `lightmaps13.bif`); K2 has one.
- **Both games have zero duplicate `(ResRef, ResType)` pairs inside the KEY.**
  Within this layer the key is unique and no precedence question arises.

**SAMPLES**
| # | file | note |
|---|---|---|
| 1 | `swkotor/chitin.key` | 26 BIFs, 25,836 resources |
| 2 | `.../steamassets/chitin.key` | 11 BIFs, 18,439 resources |
| 3 | first K1 entry: `acbonus`, type 2017, ResID 0 → bif 0 index 0 | the table is sorted, 2DAs first |
| 4 | K1 bif[4] `data\legacy.bif`, 196,688 bytes, **1 resource** | oddity: a 192 KB archive holding a single file, present in both games |

**UNKNOWN**
Whether the engine re-reads the KEY at any point after startup, and what the
drives bitmask does on a modern install. Both need the running game or a
disassembly.

## BIF — the bulk read-only data file

**WHAT IT IS**
A big undifferentiated bag of stock game resources, with no names inside it —
the names live in the KEY.

**CONTAINER**
Loose files under `data/`. Located only via the KEY.

**STRUCTURE**
Binary. Signature `BIFF`, version `V1  `. Header: variable-resource count u32,
fixed-resource count u32, offset to the variable-resource table u32.

Variable-resource entry, 16 bytes: ResID u32, offset u32, size u32,
**ResType u32**.

`FixedResCount` is **0 in every BIF checked** in both games — the fixed-resource
mechanism is present in the format and unused in the shipped data.

Note the redundancy: the ResType is stored both here and in the KEY.

**REFERENCES OUT**
Nothing. A BIF is a byte container; its entries carry no cross-references. The
resources *inside* it reference other things, but that belongs to their own
records (batches 2–6).

**REFERENCED BY**
`chitin.key`, by filename, and by BIF index inside every ResID.

**SCOPE**
Game-global, read-only.

**AUTHORED BY**
Generated by the build.

**READ WHEN**
Opened on demand and read by offset. Inferred from the format's design (an
index plus offsets, with no whole-file structure needing a full parse); residency
not confirmed.

**K1 vs K2**
- K1: 26 files, ~1,255 MB. K2: 11 files, ~1,186 MB.
- K1 splits by asset kind *and* by volume (13 lightmap BIFs); K2 splits by
  asset kind only.
- K2 introduces `scripts.bif` (1,250 resources) and `sounds.bif` (2,265) as
  first-class BIFs; K1 has no equivalent named BIFs.
- `legacy.bif` exists in both, holding exactly **1** resource in each.

**SAMPLES**
| # | file | size | resources | why chosen |
|---|---|---|---|---|
| 1 | K1 `data/2da.bif` | 431,840 b | 209 | minimal-ish, and the rules layer |
| 2 | K2 `data/models.bif` | 866,238,402 b | 8,338 | the large one — 73% of K2's whole BIF layer |
| 3 | K1 `data/legacy.bif` | 196,688 b | 1 | oddity — a named archive for a single resource, in both games |
| 4 | K2 `data/2da.bif` | 908,682 b | 424 | same role as #1, doubled — the rules growth from K1 to K2 |
| 5 | K1 `data/items.bif` | 16,362,316 b | 610 | mid-size, single-purpose |

**UNKNOWN**
What the fixed-resource table was for. It is declared in the header, is zero
everywhere in both games, and I found no writer or reader for it — searched both
binaries for adjacent diagnostics and found none. Would need a disassembly, or
an Aurora-era BIF that uses it.

## ERF — the general-purpose named archive

**WHAT IT IS**
A container that holds its own names, so it can be added to the game without
touching the master index.

**CONTAINER**
Loose files. K1: `patch.erf` at the install root, `TexturePacks/*.erf`.
K2: `modules/*_dlg.erf`, `texturepacks/*.erf`.

**STRUCTURE**
Binary. Signature `ERF `, version `V1.0`. Header, all u32 after the two tags:
language count, localized-string size, entry count, offset to localized string,
offset to key list, offset to resource list, build year, build day,
description StrRef.

- Key entry, 24 bytes: ResRef[16], ResID u32, **ResType u16**, unused u16.
- Resource entry, 8 bytes: offset u32, size u32.

The key list and the resource list are parallel arrays indexed together.
`LanguageCount` is **0** in every ERF-family file checked in both games — the
localized description block is declared and unused.

**REFERENCES OUT**
Nothing structural. `DescriptionStrRef` points into the TLK by numeric StrRef,
and is **unset or junk in shipped files** (`0`, `4294967295`, and values like
`1159751020` and `3452816845` that are not plausible StrRefs).

**REFERENCED BY**
The engine, by namespace-prefixed path (`OVERRIDE:`, `MODULES:`, and so on) —
never by another data file. Searched every 2DA in both games for archive
filenames and found none.

**SCOPE**
Depends on location, not on the format: `patch.erf` and `texturepacks/` are
game-global; `modules/*_dlg.erf` is module-local.

**AUTHORED BY**
Generated by the build or by a packing tool. Community mod installers write
ERF-family files directly.

**READ WHEN**
Directory-level ERFs at game start; module-scoped ones at module load. Inferred
from placement, not confirmed.

**K1 vs K2**
- **K1 has `patch.erf`; K2 has none.** Searched both install trees.
- **K2 uses ERF for per-module dialogue (82 `*_dlg.erf`); K1 has zero.**
  Confirmed exhaustively: 113 of K1's 117 `*_s.rim` contain DLG resources and
  K1 has no `*_dlg.erf`; **0 of K2's 82 `*_s.rim` contain DLG** and K2 has 82
  `*_dlg.erf`. This confirms the claim in the brief exactly.
- Texture packs are the same shape in both: four files, one `_gui` plus
  `tpa`/`tpb`/`tpc`. **The three `tp*` packs carry identical ResRef sets**
  (K1 3,294 each, K2 3,286 each, 100% overlap) and are disjoint from the BIF
  layer. They are quality tiers selected between, not layers stacked.

**SAMPLES**
| # | file | size | entries | why chosen |
|---|---|---|---|---|
| 1 | K2 `modules/262tel_dlg.erf` | 2,827,646 b | 24 (all DLG) | minimal and single-purpose |
| 2 | K1 `TexturePacks/swpc_tex_gui.erf` | 111,598,685 b | 1,571 | the large one |
| 3 | K1 `patch.erf` | 7,243,543 b | 97 | the oddity — see PRECEDENCE in the batch README |
| 4 | K1 `TexturePacks/swpc_tex_tpa.erf` | — | 3,294 | identical ResRef set to `tpb` and `tpc` |

**UNKNOWN**
Whether `DescriptionStrRef` is read at all. It holds implausible values in
shipped files, which suggests uninitialised memory rather than intent, but I did
not find a reader — searched both binaries for adjacent diagnostics.

## RIM — the read-only module archive

**WHAT IT IS**
The same idea as an ERF, in a simpler format, used for module content that the
game never writes back.

**CONTAINER**
Loose files. K1: `modules/*.rim`, `rims/*.rim`. K2: `modules/*.rim`.

**STRUCTURE**
Binary. Signature `RIM `, version `V1.0`. Header: reserved u32 (**0** in every
file checked), entry count u32, offset to entries u32.

Entry, 32 bytes: ResRef[16], **ResType u32**, ResID u32, offset u32, size u32.

Single table — no split key/resource arrays, no localized-string block, no build
date. **ResType is u32 here and u16 in ERF**: the two formats are not
interchangeable at the byte level despite holding the same kind of payload.

**REFERENCES OUT**
Nothing structural.

**REFERENCED BY**
The engine, by namespace path. `RIMS:GLOBAL`, `RIMS:CHARGEN`, `RIMS:MAINMENU`
are literal strings in both binaries, so those specific archives are addressed
by name rather than discovered.

**SCOPE**
`modules/*.rim` is module-local. `rims/*.rim` is game-global.

**AUTHORED BY**
Generated by the build.

**READ WHEN**
`rims/` archives at the phase they are named for; `modules/` archives at module
load. The phase association is read from the binary literals above; residency is
not confirmed.

**K1 vs K2**
- **K1 has a `rims/` directory (12 files, 37.2 MB); K2 has none.** Searched the
  whole K2 tree.
- K1 `modules/`: 234 `.rim` (117 base + 117 `_s`). K2: 164 (82 + 82).
- K1 `rims/` ships `dx` twins for every archive (`global.rim` + `globaldx.rim`).
  What `dx` selects is not established.
- Every K1 `rims/` resource also exists in the BIF layer — **1,192 of 1,192,
  100% overlap.**

**SAMPLES**
| # | file | size | entries | why chosen |
|---|---|---|---|---|
| 1 | K1 `modules/danm13.rim` | 57,765 b | 3 — ARE, GIT, IFO | minimal: the canonical module triple |
| 2 | K1 `rims/global.rim` | 20,718,578 b | 949 | the large one |
| 3 | K1 `rims/legal.rim` | 120 b | **0** | oddity — a valid, empty archive |
| 4 | K2 `modules/262tel_s.rim` | 831,168 b | 211 | typical module content payload |
| 5 | K1 `modules/danm13_s.rim` | — | 461 | the K1 shape, dialogue included |

**UNKNOWN**
What the `dx` twins in `rims/` select for, and why 4 of the 12 files
(`legal.rim`, `legaldx.rim`, `subglobal.rim`, `subglobaldx.rim`) are valid but
empty. Header parses cleanly; entry count is genuinely zero.

## MOD — the writable module archive

**WHAT IT IS**
Byte-for-byte an ERF with a different four-character signature, used where a
module needs to be a single self-contained file.

**CONTAINER**
Loose files. K1: `modules/*.mod` (40), `lips/*.mod` (123),
`currentgame/*.mod` (1). K2: `lips/*.mod` (77).

**STRUCTURE**
Identical to ERF — same header layout, same 24-byte key entries, same 8-byte
resource entries. **Only the signature differs** (`MOD ` vs `ERF `). Parsed with
one code path in both cases and every field lands correctly.

**REFERENCES OUT**
Nothing structural.

**REFERENCED BY**
The engine, by namespace path — `MODULES:`, `LIPS:%s_loc`, `CURRENTGAME:`.
The `LIPS:%s_loc` format string shows the lip archive name is *derived from the
module name*, not stored anywhere.

**SCOPE**
Module-local.

**AUTHORED BY**
Generated by the build. This is also the format community module installers
produce.

**READ WHEN**
At module load. `currentgame/` is written during play — the presence of one
`.mod` there, matching the last-played module, is read from the install; the
write path is inferred, not observed.

**K1 vs K2**
- **K1 uses `.mod` in `modules/`; K2 does not.** K2's `modules/` holds only
  `.rim` and `_dlg.erf`.
- **Correction to the brief.** The claim was "40 K1 modules ship as `.mod`
  rather than paired `.rim`." There are 40 `.mod` files, but **34 of them also
  have a `.rim` pair** — only **6** are `.mod`-only, all of them the Rakata
  endgame set (`unk_m41ae` … `unk_m41aj`). Of the 34 that coexist with a pair:
  **12 hold exactly the same resource set** as `rim + _s.rim`, **21 are a strict
  superset**, and 1 is neither. So `.mod` in K1 is mostly a *duplicate* of the
  pair, not a replacement for it.
  Example: `danm13.mod` has 468 entries against the pair's 464 — the extra four
  are UTC blueprints (`dp_danjedifc2`, `dp_danjediftw`, `dp_danjedimb2`,
  `dp_danjedimtw`).
- Both games use `.mod` for `lips/`, holding only LIP resources.

**SAMPLES**
| # | file | size | entries | why chosen |
|---|---|---|---|---|
| 1 | K1 `lips/M12ab_loc.mod` | 160 b | **0** | minimal — oddity, a valid empty archive; 14 of K1's 123 lip files are empty, and 2 of K2's 77 |
| 2 | K1 `modules/danm13.mod` | 1,632,980 b | 468 | the large one, and the superset case |
| 3 | K1 `currentgame/ebo_m12aa.mod` | 530,315 b | 321 | oddity — a live runtime artifact, not shipped content |
| 4 | K2 `lips/001ebo_loc.mod` | — | 184 (all LIP) | the K2 lip shape |
| 5 | K1 `modules/unk_m41ae.mod` | — | — | one of the 6 `.mod`-only modules |

**UNKNOWN**
Why 34 modules ship both a `.mod` and a `.rim` pair, and which the engine loads
when both are present. This is the single most consequential open question in
the batch and it needs the running game or a disassembly.

## SAV — the saved game, an archive of archives

**WHAT IT IS**
A save file that stores the mutable half of every module the player has visited,
each as a miniature module archive nested inside the save.

**CONTAINER**
Loose file inside a per-save directory: `Saves/<NNNNNN - Name>/SAVEGAME.sav`.

**STRUCTURE**
**The save file carries the `MOD ` signature, not `SAV `** — read from
`SAVEGAME.sav`, whose first eight bytes are `MOD V1.0`. `SAV` (ResType 2057)
is the type of the *entries inside it*, not the file's own tag.

A save directory holds five loose files:

```
SAVEGAME.sav     the nested archive          (MOD-signature ERF)
GLOBALVARS.res   global variable values
PARTYTABLE.res   party roster and state
pifo.ifo         module-entry info
savenfo.res      save metadata for the load screen
```

`SAVEGAME.sav` from a real autosave, 12,654,742 bytes, 28 entries:

- **6 × UTC** — `AVAILNPC0/1/2/6/7/8`, the recruitable companions' records
- **1 × RES (type 0)** — `INVENTORY`, its own GFF with magic `INV `
- **1 × FAC** — `REPUTE`, faction reputation
- **20 × SAV (type 2057)** — one per visited module

Each of those 20 is **itself a `MOD `-signature archive** containing exactly
three resources: **ARE, GIT, IFO**. Verified by extracting one (`tar_m02aa`,
799,056 bytes) and parsing it as an archive in its own right.

So a save is a two-level tree, and the leaf is the same triple that the base
`modules/<name>.rim` ships. The save stores a **replacement copy of each
module's dynamic layer**.

**REFERENCES OUT**
To modules **by ResRef**, matching the shipped module name (`tar_m02aa` is the
name of a real K1 module). To companions by fixed slot number in the ResRef
itself (`AVAILNPC0`…), which is positional, not an id.

**REFERENCED BY**
The load-game UI, via `savenfo.res`. The engine addresses the family by
`SAVES:`, `SAVES:%06d - %s`, `GAMEINPROGRESS:`, `GAMEINPROGRESS:INVENTORY`,
`GAMEINPROGRESS:PC` — literals present in both binaries, plus
`GAMEINPROGRESS:REPUTE` in both.

**SCOPE**
Campaign-level. One tree per save slot.

**AUTHORED BY**
Written by the engine. Never authored.

**READ WHEN**
On load. Written on save and, from the `gameinprogress/` and `currentgame/`
directories, during play — the live working set exists as loose files
(`AVAILNPC0.utc`, `AVAILNPC1.utc`) alongside a `.mod` of the active module.
That these are the live working copies is inferred from their location and the
matching namespace literals; the write path was not observed.

**K1 vs K2**
Structure not compared. **K1 only** — this install's K2 has no save directory
under `steamassets` and no saves were present to read. The K1 shape above should
not be assumed to hold for K2 until a K2 save is examined. The
`GAMEINPROGRESS:` and `CURRENTGAME:` literals are present in the K2 binary, so
the mechanism exists; the layout is unverified.

**SAMPLES**
| # | file | size | entries | why chosen |
|---|---|---|---|---|
| 1 | K1 `Saves/000001 - AUTOSAVE/SAVEGAME.sav` | 12,654,742 b | 28 | the whole shape |
| 2 | nested `tar_m02aa` inside #1 | 799,056 b | 3 — ARE, GIT, IFO | minimal: the leaf |
| 3 | nested `tar_m02ab` inside #1 | 3,365,181 b | 3 | the large leaf — same 3 resources, 4× the bytes |
| 4 | K1 `Saves/000021 - Game20/` | — | **`savenfo.res` only** | oddity — a save directory with metadata and no save |
| 5 | K1 `currentgame/ebo_m12aa.mod` | 530,315 b | 321 | the live counterpart to a nested leaf |

**UNKNOWN**
The internal structure of `GLOBALVARS.res`, `PARTYTABLE.res` and `savenfo.res`
— they are GFF-family by magic but were not parsed in this batch (that is
batch 2/4 territory). Also unknown: why three save directories in this install
contain only `savenfo.res`, and whether the engine prunes visited-module
snapshots or accumulates them without limit.
