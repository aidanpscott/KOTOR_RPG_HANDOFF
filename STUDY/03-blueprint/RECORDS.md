## GFF — the object record format

**WHAT IT IS**
A generic tree of named fields — the container every blueprint, area file and
save record is written in.

**CONTAINER**
BIF and module archives. Never standalone except in save directories.

**STRUCTURE**
Binary. Four-character type tag (`UTC `, `UTI `, `GIT `…), version `V3.2` on
**every one of the 3,097 blueprints checked in both games** — no other version
ships.

Header: twelve uint32 giving offset and count for six arrays.

```
Struct array   12 b each:  Type u32, DataOrDataOffset u32, FieldCount u32
Field array    12 b each:  Type u32, LabelIndex u32, DataOrDataOffset u32
Label array    16 b each:  fixed-width field name
FieldData      variable-length values (strings, resrefs, 64-bit numbers)
FieldIndices   u32 list, used when a struct has more than one field
ListIndices    u32 count + struct indices, used by List fields
```

A **struct** is a set of fields. A **list** is an array of struct indices. The
difference at the byte level: a field of type 14 (`Struct`) holds one struct
index directly; type 15 (`List`) holds an offset into ListIndices, which begins
with a count.

**Nineteen field types are defined. Eleven are used by blueprints; eight never
are:**

```
used     BYTE CHAR WORD SHORT DWORD INT FLOAT
         CExoString ResRef CExoLocString List
UNUSED   DOUBLE DWORD64 INT64 Orientation Vector VOID StrRef Struct
```

Two of those absences matter.

**`StrRef` (type 18) is never used by any blueprint.** Every string reference
travels inside a `CExoLocString`, which carries a StrRef *and* an optional list
of inline substrings. So the format has a dedicated string-reference type and
the content does not use it.

**`Struct` (type 14) is never used by any blueprint.** Nesting only ever happens
through lists. A blueprint is therefore always a flat record plus arrays — never
a struct containing a struct.

**⚠ Is GFF self-describing? Structurally yes, semantically no — and the gap is
the whole problem.**

*What the file tells you without a schema:* every field's name, its type, the
tree shape, list lengths. A reader with no prior knowledge can walk a UTC and
print `Appearance_Type = 452` correctly.

*What it does not tell you:* that `452` is a row index into `appearance.2da`.
Nothing in the file names the target table, and nothing distinguishes an index
from a quantity. `Str = 14` and `Race = 6` have the same type and the same
shape; one is a value and one is a pointer. **The reference graph is not in the
data.** This is batch 2's F13 (untyped 2DA cells) reappearing one layer up.

**⚠ And the struct type id carries data, not just schema.**
In most lists the struct type is a constant schema tag — `SkillList` 0,
`FeatList` 1, `ClassList` 2, `SpecAbilityList` 4. But:

- **`Equip_ItemList` uses the struct type as the equipment slot bitmask.**
  13 distinct values in both games — 1, 2, 16, 32, 256, 1024, 16384, 32768,
  65536, 131072 — which match the hex values in `baseitems.equipableslots`
  (`0x00001`, `0x00002`, `0x00010`, `0x00020`, `0x00100`, `0x00400`, `0x04000`,
  `0x08000`, `0x10000`, `0x20000`).
- **`ItemList` uses the struct type as the inventory sequence number** — 0, 1,
  2, 3 … 34 distinct values in K1.

A format-level field meant to identify a struct's *schema* is carrying
*payload*. See `FLAWS.md` F24.

**REFERENCES OUT** Nothing — GFF is the carrier. Its *contents* reference by
ResRef (string), 2DA row index (integer) and StrRef (inside CExoLocString).

**REFERENCED BY** Every blueprint, area file and save record.

**SCOPE** Format — no scope of its own.

**AUTHORED BY** Generated by the toolset.

**READ WHEN** Whenever the resource is loaded.

**K1 vs K2** No format differences found. Same version, same type set, same
header layout. The only difference is which field *names* appear — see the
individual records.

## UTC — creature blueprint

*The richest type, and the field-by-field pass the brief asked for.*

**WHAT IT IS** Everything about a creature that does not depend on where it is
standing.

**CONTAINER** BIF (205 K1, 284 K2) and module archives (1,589 K1 / 932 K2
distinct resrefs). Read in full: **2,656 K1 and 1,741 K2 files.**

**STRUCTURE** GFF, tag `UTC `, V3.2. Field groups below. Percentages are
presence across all files of that game.

**① Identity** — `TemplateResRef` (ResRef, its own name), `Tag` (string),
`Comment` (string, author notes shipped in the data), `FirstName` and `LastName`
(CExoLocString), `Description` (CExoLocString), `PaletteID` (index into
`crtemplates.2da`, a toolset grouping).

**② Attributes** — `Str` `Dex` `Con` `Int` `Wis` `Cha`, BYTE, 100% both games.

**③ Vitals and derived** — `HitPoints`, `CurrentHitPoints`, `MaxHitPoints`,
`ForcePoints`, `CurrentForce`, `NaturalAC`, `ChallengeRating` (FLOAT),
`fortbonus` / `refbonus` / `willbonus`.

**④ Progression — the four lists, and the asymmetry this batch exists to map**

```
ClassList        [{Class, ClassLevel, KnownList0}]           struct type 2
    KnownList0   [{Spell, SpellMetaMagic, SpellFlags}]       explicit id
FeatList         [{Feat}]                                    struct type 1
SkillList        [{Rank}]  ← 8 entries, NO ID                struct type 0
SpecAbilityList  [{Spell, SpellCasterLevel, SpellFlags}]     struct type 4
```

`ClassList` is 1 entry in 2,641 of 2,656 K1 files (14 have 2, one has 3).
`FeatList` length runs 0–5+ and carries an explicit `Feat` row index per entry.
`KnownList0` carries an explicit `Spell` row index.

**`SkillList` alone carries no identifier.** Eight entries, each `{Rank}`,
position implying which skill. Confirmed across 2,653 of 2,656 K1 files and
**1,741 of 1,741 K2 files**.

**Oddity, and it proves nothing validates the length:** three K1 BIF blueprints
ship a **20-entry** `SkillList` — `c_drdg`, `c_sebulba` and `partymember`. They
are not padding: `partymember` carries rank 4 at index 18, well past the eighth
slot. `c_sebulba` is a prequel-film character with no place in either game.

**⑤ Appearance** — `Appearance_Type` (row index into `appearance.2da`),
`PortraitId` (`portraits.2da`), `Race` (`racialtypes.2da`), `Subrace` (string)
*and* `SubraceIndex` (int into `subrace.2da`), `Gender` (`gender.2da`),
`Phenotype`, `BodyVariation`, `TextureVar`, `SoundSetFile`.

Range checking those indices against their target tables:

```
K1  Appearance_Type   1..546  vs appearance.2da 509 rows   ⚠ OVERFLOWS by 38
    Race              2..8    vs racialtypes.2da  7 rows   ⚠ OVERFLOWS by 2
    SoundSetFile      1..65535                             65535 = "none" sentinel
K2  Appearance_Type   2..670  vs appearance.2da 671 rows     fits
    Race              5..6    vs racialtypes.2da  7 rows     fits
```

**The K1 appearance overflow is real and it is confined.** 82 occurrences, 78
distinct resrefs, and **all 82 are in `.mod` files — zero in `.rim`, zero in
BIF.** 36 of the 78 also exist in a `_s.rim` with a valid value. See `FLAWS.md`
F25; this bears on batch 1's F08.

**⑥ Alignment** — `GoodEvil` (0–100 scale) and `LawfulChaotic`, both 100% in
both games. KOTOR uses one axis; the second is inherited and carried anyway.

**⑦ Behaviour and flags** — `FactionID` (`repute.2da` row), `PerceptionRange`,
`WalkRate`, `Disarmable`, `Interruptable`, `NoPermDeath`, `Min1HP`, `Plot`,
`IsPC`, `PartyInteract`, `NotReorienting`. K2 promotes five K1 rarities to
near-universal: `BlindSpot` (88.7%), `Hologram` (85.9%), `MultiplierSet`
(84.7%), `IgnoreCrePath` (75.0%), `WillNotRender` (66.5%) — each appears on
exactly **one** K1 file.

**⑧ Inventory** — `Equip_ItemList` `[{EquippedRes[, Dropable]}]`, **slot carried
in the struct type id**; `ItemList` `[{InventoryRes, Repos_PosX, Repos_Posy
[, Dropable]}]`, **sequence carried in the struct type id**.

*Oddity:* `Repos_Posy` (lowercase y) in 1,468 K1 entries and `Repos_PosY`
(uppercase) in 139. The same field, two spellings, both shipped.

**⑨ Scripts** — fourteen ResRef hooks: `ScriptAttacked`, `ScriptDamaged`,
`ScriptDeath`, `ScriptDialogue`, `ScriptDisturbed`, `ScriptEndDialogu` (name
truncated to fit the 16-byte label), `ScriptEndRound`, `ScriptHeartbeat`,
`ScriptOnBlocked`, `ScriptOnNotice`, `ScriptRested`, `ScriptSpawn`,
`ScriptSpellAt`, `ScriptUserDefine`. Plus `Conversation` (ResRef to a DLG).

**⑩ Dead and vestigial** — `TemplateList` is a List that is **length 0 in all
2,653 K1 and all 1,741 K2 files**. `Deity` is present at 100% in both games and
is an NWN field with no KOTOR meaning. K1 additionally ships, on 1–3 files each:
`Tail`, `Wings`, `Morale`, `MoraleBreakpoint`, `MoraleRecovery`,
`SaveFortitude`/`SaveReflex`/`SaveWill`, `Appearance_Head`, `SoundSet`,
`SubRace` (a third spelling), and `FortBonus`/`RefBonus`/`WillBonus` — **case
variants of the lowercase fields carried by 2,596 files.**

`KTGameVerIndex`, `KTInfoDate`, `KTInfoVersion` appear on 55 K1 files: toolset
metadata shipped in the product. Absent from K2 entirely.

**REFERENCES OUT** ResRef (scripts, conversation, equipped and carried items,
its own template name); 2DA row index (appearance, portrait, race, gender,
subrace, faction, palette, body bag, feats, classes, powers); StrRef inside
CExoLocString (names, description); **and position, for skills.**

**REFERENCED BY** `GIT` `Creature List` entries by `TemplateResRef`; `UTE`
spawn lists by `ResRef`; save records; scripts by tag.

**SCOPE** Blueprint is module-local when in a module archive, game-global when
in the BIF. Same file, scope decided by where it sits.

**AUTHORED BY** A human in the toolset. The `Comment` field and the `KTInfo*`
fields are direct evidence.

**READ WHEN** At spawn.

**K1 vs K2** K2 is markedly cleaner: 100% presence on nearly every field where
K1 has stragglers; the 20-entry `SkillList` outliers are gone; case-variant
fields are gone; `KTInfo*` is gone. K2 adds no new field group — it standardises
five K1 experiments and drops the NWN residue.

## UTI — item blueprint

**WHAT IT IS** An item: what it is, what it is worth, and what it does.

**CONTAINER** BIF (557 K1, 994 K2) and modules. Read: 1,170 K1, 1,198 K2.

**STRUCTURE** GFF, tag `UTI `. **16 fields always present:** `BaseItem`,
`Cost`, `AddCost`, `Charges`, `StackSize`, `Plot`, `Stolen`, `Identified`,
`LocalizedName`, `Description`, `DescIdentified`, `PropertiesList`, `Tag`,
`TemplateResRef`, `Comment`, `PaletteID`. Optional: `ModelVariation` (91% K2),
`UpgradeLevel` (87%, **K2 only**), `BodyVariation` / `TextureVar` (9%).

**⚠ The property system — the answer to "data or code?": entirely data, through
five levels of table indirection.**

A `PropertiesList` entry:

```
{PropertyName, Subtype, CostTable, CostValue, Param1, Param1Value,
 ChanceAppear [, UpgradeType]}
```

- `PropertyName` → row index into **`itempropdef.2da`** (60 K1 / 70 K2 rows)
- that row's `subtyperesref` column **names another 2DA by string** — 20 distinct
  targets in K1, 23 in K2, including `appearance`, `classes`, `feat`, `gender`
  and the whole `iprp_*` family
- `Subtype` → row index into *that* named table
- `CostTable` → row index into **`iprp_costtable.2da`** (26 K1 / 27 K2 rows),
  which names the table holding cost values
- `CostValue` → row index into that
- `Param1` → row index into **`iprp_paramtable.2da`** (12 rows both games);
  `Param1Value` → row index into the table it names

**No script is involved anywhere.** An item's mechanical effect is a chain of
integer row indices terminating in 2DA cells.

*Naming defect:* `itempropdef.2da`'s `costtableresref` and `param1resref`
columns are named as if they hold ResRefs. Their values are decimal strings —
`'0'`, `'1'`, `'11'`, `'14'` — i.e. row indices. Only `subtyperesref` actually
holds table names. See `FLAWS.md` F27.

Properties per item: 573 of 1,170 K1 items have **none**; the maximum observed
is 7+.

**REFERENCES OUT** `BaseItem` → `baseitems.2da` row; the property chain above;
`LocalizedName` / `Description` / `DescIdentified` → StrRef; `ModelVariation`
→ model set.

**REFERENCED BY** `UTC.Equip_ItemList.EquippedRes` and `UTC.ItemList.
InventoryRes` by ResRef; `UTP.ItemList`; `UTM.ItemList`.

**SCOPE** Module-local or game-global by location.

**AUTHORED BY** A human in the toolset.

**READ WHEN** At spawn or on inventory load.

**K1 vs K2** K1 has `ModelPart1/2/3` and `KTGameVerIndex`/`KTInfoDate`/
`KTInfoVersion`; K2 replaces the model triple with `ModelVariation` and adds
**`UpgradeLevel`**, the hook for the upgrade system. `upgradetypes.2da` grows
10 → 12 rows and `upcrystals.2da` 7 → 14.

**SAMPLES**
| # | file | source | why |
|---|---|---|---|
| 1 | `g_i_credits001.uti` | K1 BIF | minimal — 0 properties |
| 2 | `g_w_lghtsbr01.uti` | K2 BIF | elaborate — properties with `UpgradeType` |
| 3 | `mininglaser.uti` | K2 `101per_s.rim` | oddity — module copy differs from the BIF copy (683 → 955 b) |
| 4 | `g_i_belt011.uti` | K1 | one of the 14 UTIs shadowing a BIF resource from a module |

**WHAT IT IS** A spawn rule: what appears, how many, how often.

**CONTAINER** BIF (65 in both games) and modules. Read: 161 K1, 115 K2.

**STRUCTURE** GFF, tag `UTE `. 22 fields, all always present.
`Active`, `Difficulty`, `DifficultyIndex`, `MaxCreatures`, `RecCreatures`,
`Respawns`, `Reset`, `ResetTime`, `SpawnOption`, `PlayerOnly`, `Faction`,
four script hooks (`OnEntered`, `OnExit`, `OnExhausted`, `OnHeartbeat`,
`OnUserDefined`), and `CreatureList`.

`CreatureList` entries: `{ResRef, Appearance, CR, SingleSpawn [,
GuaranteedCount]}` — **note `ResRef` again, not `TemplateResRef`**, and note
that the entry duplicates `Appearance` and `CR` which already live on the UTC it
names.

**REFERENCES OUT** `CreatureList[].ResRef` → UTC by ResRef; `Faction` →
`repute.2da`; scripts by ResRef.

**REFERENCED BY** `GIT` `Encounter List`; the instance adds `Geometry` and
`SpawnPointList`.

**SCOPE** Module-local or game-global by location.

**AUTHORED BY** Human.

**READ WHEN** Area load; fires during play.

**K1 vs K2** Identical field sets.

**SAMPLES**
| # | file | source | why |
|---|---|---|---|
| 1 | a single-creature encounter | K2 modules | minimal |
| 2 | a multi-entry `CreatureList` with `GuaranteedCount` | K1 modules | elaborate |
| 3 | any UTE | both | oddity — `Appearance` and `CR` duplicated from the creature it spawns, with nothing keeping them in step |

**UNKNOWN** Whether the engine uses the encounter's copy of `Appearance`/`CR`
or the creature's. Needs the running game — and it matters, because they can
disagree.
